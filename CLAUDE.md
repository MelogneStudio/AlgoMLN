# CLAUDE.md

AlgoMLN is a local-first algorithmic trading platform — engine-first Rust, thin Tauri + React UI. Strategies compile from a custom DSL to an AST and are evaluated candle-by-candle deterministically against historical (or live) data, then routed to an `ExecutionTarget` (Paper or Live broker). Backtests, paper trading, and live trading share one engine — there is no separate "live code path."

```
Data → Indicators → Strategy Engine → Backtesting → Execution → UI
```

> **Documentation map.** This file is the index — project overview, run commands, invariants, and pointers. Narrative and "where to find what" details live in:
> - **`ARCHITECTURE.md`** — file tree + "where to look for X" lookup tables (DSL → which files, indicators → which files, IPC → which files, etc.)
> - **`BACKEND.md`** — narrative on the Rust crate: DSL pipeline, runtime/evaluation loop, execution targets, Tauri commands, CLI, data flow
> - **`FRONTEND.md`** — narrative on the React app: shell/scaling, screen state machine, builder↔coder round-trip, IPC hooks, wire types

## Common Commands

Run from the repo root. Rust is the source of truth; the UI is a thin client.

### Tests
```powershell
cargo test --workspace                  # full Rust test suite
cargo test --lib strategy::             # only strategy tests
cargo test --lib -- test_name_substring # single test by name substring
```

### Backtest CLI
`behavioral_backtest` runs any `.algomln` strategy against CSV data. Sample NIFTY 1-min data lives in `sample-data/`.

```powershell
cargo run --release --bin behavioral_backtest -- run my_strategy.algomln --data sample-data/nifty_1min.csv --symbol NIFTY
cargo run --release --bin behavioral_backtest -- run my_strategy.algomln --data sample-data/nifty_1min.csv --candles 10000 --cash 500000
cargo run --release --bin behavioral_backtest -- profile rsi 50000
```

### Tauri App
```powershell
npm install            # first time
npm run tauri dev      # Vite + Tauri together
npm run dev            # frontend-only dev server
npm run build          # type-check + production frontend build
```

There is no separate linter step — `npm run build` runs `tsc` and acts as the de-facto type check.

### First-time setup

```powershell
python scripts/fetch_seed_indices.py   # populates src-tauri/resources/indices/*.json (stdlib only)
```

Run this once from the repo root before the first `npm run tauri dev` so the bundled index seed files are present. The Rust app also tolerates a missing seed (each alias falls back to an empty list and the user can refresh in Settings).

## Critical Architecture Invariants

Don't break these — they are non-obvious properties the codebase is built around.

**1. Determinism.** Same strategy + same candles = identical output. Use `BTreeMap` over `HashMap` anywhere iteration order could affect evaluation. No randomness on eval paths. The engine uses `BTreeMap`-backed registries. (Guarded by a dedicated test.)

**2. Trigger state machine.** A bare `WHEN x > y / BUY 1` would fire every candle. `TriggerStateMap` fires rules only on `false → true` transitions. `CrossDetector` stores `(fast_prev, slow_prev)` and fires on the exact transition candle. Critically: the cross update pass runs **after** all rules are evaluated for the cycle — not inside the rule loop — so every rule sees consistent previous-candle state within a single cycle. See `src/strategy/runtime/cross.rs` + `trigger_state.rs`, called from `engine.rs::on_candle`.

**3. One execution engine.** Backtests, paper, and live all run through `StrategyEngine` + `ExecutionTarget`. The engine never knows which broker is behind the target. `PaperBroker` and `DhanBroker` are interchangeable implementations. `DhanBroker` wraps `DhanClient` for `/orders` and `/positions`; order placement resolves symbols through the shared `SymbolMap`. (`src/strategy/execution/`.)

**4. Indicator windows are bounded.** `BoundedWindowProvider` keeps indicators O(N) — 184,863 NIFTY 1-min candles complete in ~3.5s (~52k candles/sec). Don't refactor into naive full-history recomputation. (`src/strategy/runtime/incremental_provider.rs`.)

**5. DSL grammar is intentionally small.** Rules only — no variables, no loops. Keywords case-insensitive. Indicator periods and quantities must be positive integers. `position_expr` and `time_window` parse but are not yet evaluated at runtime — see `src/strategy/dsl/ast.rs` and the `NotYetImplemented` branch in the evaluator.

**6. Wire-format boundary.** Rust types crossing the IPC boundary serialize to camelCase JSON (`#[serde(rename_all = "camelCase")]`). Internal `BacktestResult` / `PaperTrade` keep snake_case Rust field names; the conversion happens in `commands::strategy::BacktestResultWire` and `PaperTradeWire`. If you add a field the UI consumes, add it to the wire struct AND mirror it on the TS side — don't put extra UI-relevant fields directly on `BacktestResult` and rely on Rust serde to rename.

**7. Plugin capability gating.** Plugins reach the engine only through `PluginHost`'s `*_guarded` accessors (`src/plugin/host.rs`). The accessor checks the plugin's declared `Capability` list and returns `PluginError::PermissionDenied` if the capability is missing. `LogApi` is intentionally unguarded. The plugin layer ships capability implementations for market data (broker-backed), per-plugin file KV storage, indicator/analytics/DSL-extension registries with plugin-id dedup, a **read-only** execution API (`ReadOnlyLiveExecutionApi`) that exposes positions during a live session but rejects order submission, a broadcast event bus, cron scheduling, and a Tauri-broadcast UI API — see `src/plugin/api/`. The Rhai script runtime is live in `src/plugin/runtime/rhai_runtime.rs` (hardened engine, capability-gated host fns, lifecycle dispatch). The WASM plugin runtime is live in `src/plugin/runtime/wasm_runtime.rs` (wasmtime 23, capability-gated `algomln::*` host fns, bounded linear memory via `ResourceLimiter`, epoch-interruption-armed store; WASI is intentionally not linked because `WasiCtx` in wasmtime 23 is `Send`-only and would violate the `Plugin: Send + Sync` bound). The plugin loader (`src/plugin/loader.rs`) dispatches on entry extension to `RhaiPlugin` or `WasmPlugin`. The plugin registry (`src/plugin/registry.rs`) holds the in-memory plugin map, calls each plugin's `on_load` with a `PluginHost` built by a caller-supplied factory, and tracks `Loaded` / `Enabled` / `Disabled` / `Failed` per plugin. The plugin API surface in `src/plugin/api/mod.rs` is plugin-id-attributed: `IndicatorRegistryApi::register` / `AnalyticsApi::register_metric` / `DslExtensionApi::register_keyword` all take a `PluginId`; `SchedulerApi::cancel_all_for(plugin_id)` and `DslExtensionApi::unregister_all_for(plugin_id)` let the registry reclaim per-plugin entries on disable.

**7a. Plugin log rate-limiting and rolling files.** The Tauri host factory wires every plugin's `LogApi` to a `RateLimitedFileLog` (`src/plugin/api/log_file.rs`) so a misbehaving or malicious plugin cannot fill the user's SSD by spamming `log_info` / `log_warn` / `log_error`. The rate limiter is a per-plugin token bucket: default 10 msg/sec burst, 100 msg/min sustained, shared across all log levels; excess messages are silently dropped, with a single per-minute `[plugin:<id>] [WARN] rate-limited: N message(s) dropped in the last 60s` summary line so the user can see throttling is happening. Output goes to `<app_data>/logs/plugin-<id>.log` and is capped at 5MB per file — on every write that would push the on-disk size past 5MB the current file is renamed to `<base>.1` (older `*.1` overwritten) and a fresh current file is opened. The CLI binary keeps using the simpler `NamespacedLog` because it does not load plugins; the CLI path is for backtesting and profiling only.

**8. Engine event-bus gating.** `StrategyEngine` carries an `event_bus: Option<Arc<EventBus>>` (default `None`) and publishes three event kinds from `on_candle` only when the bus is `Some`: `RuleFired` after `TriggerStateMap::should_fire` returns `true` (rule-eval pass), `TradeExecuted` immediately after a successful `execution_target.execute` (paper broker recovered via `as_any` downcast on `ExecutionTarget`), and `CandleProcessed` after the cross-update pass. No event is published from the cross-update or indicator-advance passes themselves. **Backtests deliberately leave `event_bus` as `None`** (see `commands::strategy::run_backtest_internal`) so plugin callbacks never run during replay — determinism is preserved. The Tauri binary owns the live bus and assigns it to the engine only for paper/live runs (stage 9 hook in `src-tauri/src/main.rs`).

**9. Tauri plugin wiring.** `AppState` is defined in `src/commands/state.rs` (re-exported as `commands::AppState`) and carried by `tauri::Manager` so `State<'_, AppState>` works in every command. The Tauri binary's `setup` closure builds the plugin's shared infrastructure once — registries, event bus, scheduler, broker wrappers, noop execution — and wires them into a single `HostFactory` closure. `PluginRegistry::scan_and_load` runs at startup via `tauri::async_runtime::block_on` (Tauri 2's `setup` is sync). `TauriUiApi` messages are forwarded to the Tauri event bus as `"plugin-ui-message"` via a `tokio::spawn`'d forwarder; the React app subscribes once and dispatches on the `UiMessage` variant. `#[tauri::command]` wrappers for plugin commands live in `src-tauri/src/main.rs` (not the library) because the macro generates module-private artifacts that `tauri::generate_handler!` must resolve in the same scope. The four plugin commands are `list_plugins` / `enable_plugin` / `disable_plugin` / `reload_plugins`. `PluginRegistry::enable` / `disable` / `unload` swap the real plugin out of the entry under the write lock before awaiting the lifecycle callback (parking_lot guards are `!Send`, so holding one across `.await` would break Tauri's command dispatcher and risk deadlock if a plugin re-enters the registry).

**9a. Tauri index + symbol-map startup wiring.** The setup closure loads `SymbolMap` from `<app_data>/sec_id_cache.csv` (falls back to the bundled seed in `sample-data/sec_id.csv` or the bundled resource `src-tauri/resources/sample-data/sec_id.csv`) before constructing `DataState`, so `AppState` and `DhanClient` share the same hot-refreshable `Arc<RwLock<SymbolMap>>`. It also loads `IndexRegistry` from `<app_data>/indices/` (falls back to bundled `src-tauri/resources/indices/`). Two background tasks check both for staleness (90 days for indices, 7 days for the symbol map) and refresh silently on startup. The three index IPC commands — `list_indices` / `get_index_symbols` / `refresh_indices` — live in `src/commands/indices.rs` and are registered alongside the plugin commands in `tauri::generate_handler!`. `refresh_indices` is long-running (~30–60s) and writes both the index JSON and the symbol-map CSV before swapping the in-memory `SymbolMap` under its `RwLock`.

**9b. Immutable live trade log.** The Tauri setup closure opens `<app_data>/trade_log.jsonl` through `src/live/trade_log.rs::TradeLog` and stores both `Arc<TradeLog>` and `trade_log_path` in `AppState`. The log is append-only JSONL: the app creates parent directories, opens with `create(true).append(true)`, writes one compact JSON object per line, flushes after each append, and never truncates. `get_trade_log` reads from disk via `src/commands/live.rs`, skips blank lines, warns on malformed lines, and returns newest entries first. **Trade log writes are owned by `DhanBroker::execute_with_meta`** — every call to `execute` or `execute_with_meta` (regardless of call path, including future plugin execution) appends one entry. The session tick loop no longer writes to the log directly.

**9c. Single live session manager.** Phase 7 live execution is intentionally single-session. `AppState.live_session` holds `Arc<tokio::sync::Mutex<Option<Arc<LiveSession>>>>`. `src/live/session.rs::LiveSession` owns the strategy engine, Dhan broker, trade log, rolling candle history (capped at `MAX_CANDLE_HISTORY = 5000` entries — oldest candles are drained from the front on overflow), status, cancellation token, and the NSE holiday calendar used by the per-candle market-hours gate (audit item B1). It subscribes through the shared `FeedManager`, uses `src/live/candle_assembler.rs::CandleAssembler` to close 1-minute candles from ticks, appends each completed candle to history, and calls the same `StrategyEngine::on_candle` used by backtests/paper runs. `LiveSession::start` accepts an `initial_cash: f64` parameter that is threaded into `StrategyInstance::initial_cash` and used by `RISK MAX_DAILY_LOSS` — `DhanBroker` does not know the starting capital, so without this argument the cap is a silent no-op (audit item A1). The Tauri binary's `confirm_live_start` passes `DEFAULT_LIVE_INITIAL_CASH = 1_000_000.0` INR; a `<= 0.0` value triggers a stderr warning at session start so the user notices the cap won't fire. `LiveSession::start` also accepts an `Arc<NseHolidayCalendar>` cloned from `AppState.live_guard.holiday_calendar` — the same calendar `LiveGuard::run_preflight` consults at session start, so the per-candle gate can never drift from the preflight predicate. **B1 per-candle market-hours gate:** the tick loop converts each candle's `timestamp` (UTC millis) into IST and runs `is_market_open(close_ist, &holiday_calendar)` before pushing the candle into the engine pipeline. A weekend, holiday, or outside-09:15–15:30 candle is appended to `candle_history` (so indicator windows stay continuous across weekend gaps) but `plan_candle` is **not** invoked on it — no order can be submitted outside the session-start window. This closes the post-close order hazard where a session started at 15:29 would otherwise submit an order at 15:30:00.001. The gate is guarded by `test_gate_skips_weekend_candle` / `test_gate_skips_post_close_candle` / `test_gate_skips_holiday_candle` in `src/live/session.rs::tests`, plus the existing `is_market_open` predicates in `src/live/guard.rs::tests`. **Paused sessions continue to assemble candles and run `on_candle` every minute** — only new *entry* (BUY) orders are suppressed, via `DhanBroker::paused_for_entries`. Stop-loss, take-profit, and risk-breach SELL orders always execute regardless of pause state. The tick loop also auto-pauses (same mechanism) when `DhanBroker::is_stale()` is true — `is_stale()` is the OR of the realized-loss and available-cash stale flags, both raised after 3 consecutive refresh failures. `DhanBroker::available_cash()` is now backed by a polling cache of `GET /funds/limit` (`FUNDS_REFRESH_INTERVAL_SECS = 60` s), not `f64::MAX`, and is initialized to `DEFAULT_AVAILABLE_CASH_CAP` (1 lakh INR) on a cold cache so `PercentCapital` orders can never oversize past `u64::MAX`. `RecvError::Lagged` on the tick broadcast channel is non-fatal (`continue`); `RecvError::Closed` breaks the loop, sets status to `Failed("feed closed unexpectedly")`, and calls `SessionEventEmitter::emit_failed` with a `LiveSessionFailedPayload`. `SessionEventEmitter` is a trait injected into `LiveSession::start`; the Tauri binary wraps `AppHandle` in a `TauriSessionEmitter` impl, tests use `MockEmitter`, non-alert paths use `NoopEmitter`. `LiveSession::stop` cancels the task and awaits it under a 5-second drain timeout; if the tick loop is still running (e.g. an HTTP `place_order` is in flight) `stop` returns and logs a warning so the caller can surface it. Stopped sessions cancel the task. `LiveSession::start` writes a `SessionContext { strategy_id, strategy_name, mode: "live" }` onto `broker.session_context` before starting; `stop` clears it, so the broker always logs the correct session metadata regardless of which code path triggers `execute`. **H3 cancellation plumbing (Phase 8):** `LiveSession::start` constructs the session's `CancellationToken` and wires it into the broker via `DhanBroker::set_cancel_token` before subscribing to the feed. `DhanBroker::execute_with_meta` checks `cancel_token.is_cancelled()` at the very top, before the paused-for-entries check or the broker HTTP call, so a `stop()` mid-`place_order` aborts within a few hundred ms and the trade-log row is never appended. The token is stored behind a `parking_lot::RwLock<CancellationToken>` so the broker is `Arc`-shared without needing exclusive ownership. Only **fill** results (`status.is_fill()`) are written to the trade log — `Transit` / `Pending` orders are returned to the caller with their status intact but no phantom trade row is created. `DhanBroker::execute_with_meta` logs a single stderr line when an attempted placement errors at the broker.

**9d. Live-start safety gate layer.** No live order may ever be placed unless gates 1–8 pass via `src/live/guard.rs::LiveGuard::run_preflight`. The guard is the only path that issues a `PendingLiveToken`; the token is single-use, 90 s TTL, bound to a strategy id, and stored in `AppState.pending_live_token`. Gate order: paper-default (record's `mode` == Live), broker reachability (`get_positions` succeeds), symbol in map, segment == NseEq, market hours (09:15–15:30 IST Mon–Fri, NSE holiday calendar excluded), at least one risk control declared, `MAX_DAILY_LOSS` is `Some(_)` (hard, non-negotiable), broker not stale. Ack is not a gate — it picks `LiveGuardResult::Ok` vs. `RequiresAcknowledgment`; both variants carry a token. `request_live_start` holds the `live_session` slot lock across preflight **and** the token-store write so concurrent UI requests cannot race; `confirm_live_start` holds the slot lock across `LiveSession::start` so a concurrent `request_live_start` cannot slip a second session in. **Resume-during-stale guard (audit H2):** `resume_live_strategy` refuses to resume when `broker.is_stale()` is true and returns an error citing the elapsed time since the last successful refresh (driven by `DhanBroker::time_since_last_success`, which is `None` until the first refresh succeeds). This stops the user from clicking Resume while the realized-loss or available-cash cache is still unreliable and resuming with stale safety metrics. Hot path: `src/commands/live.rs`.

**10. Index data is read-only at runtime.** `IndexRegistry::update` is the only mutator; it is called only by `refresh_index` (and `load_from_dirs` at startup). Strategy engines read constituents once at deploy time and do not re-read mid-run. If constituents change (quarterly rebalance), re-deploy the strategy.

**11. PortfolioEngine sub-engines are never accessed concurrently.** `PortfolioEngine::on_tick` takes `&mut self` and is called from a single tokio task; the underlying `StrategyEngine` instances share a single `Arc<PaperBroker>`. `PaperBroker` is internally `Mutex`-guarded so the shared broker is `Send`, but the per-sub-engine state (cross detector, trigger map, indicator window) is `!Sync`. Adding parallel `on_tick` calls would require `Mutex<StrategyEngine>` per sub-engine and a careful determinism audit — do not add it without a full review.

**12. SL/TP is a safety net, not a rule.** `STOP_LOSS` and `TAKE_PROFIT` are strategy-level declarations on `StrategyNode` (not `RuleNode`s) that bypass `TriggerStateMap` deliberately. They fire every candle the position is underwater or in profit, not just on a `false → true` transition. The pass runs *after* the rule loop and the cross-state update so a rule that closes the position on the same candle is reflected. Stop-loss wins on a gap candle that would trigger both — the position is already closed by the time take-profit would check. (`src/strategy/runtime/engine.rs::run_stop_loss_take_profit_pass`, `src/strategy/dsl/parser.rs` for declarations, `src/strategy/dsl/validator.rs` for the `(0, 100]` range check.)

**13. Risk controls are evaluated before every order.** `RISK MAX_ORDERS`, `RISK MAX_POSITIONS`, and `RISK MAX_DAILY_LOSS` are strategy-level declarations (like SL/TP) on `StrategyNode.risk: Option<RiskConfig>`. The engine stores the per-run counter in `StrategyEngine::risk_state: Option<RiskState>` (allocated only when at least one declaration is present). `check_risk_breach` runs at the top of `submit_action` — before the order is built — and logs `LogEntryKind::RiskBreach { rule_id, reason }` on a hit, then returns without submitting. `session_orders` is incremented **only on a successful `execute` AND only for entry orders (BUYs)** so a failed order does not consume the cap, and exit orders never consume it. **Exits (`SELL`, `SELL ALL`, including the strategy-level SL/TP synthetic closes) are exempt from `MAX_ORDERS`** — they neither block when the cap is exhausted nor count toward it (audit item A2; the safety-net guarantee from invariant 12). `MAX_POSITIONS` only blocks BUYs; sells (including SL/TP `SELL ALL`s) are never blocked by it. `MAX_DAILY_LOSS` is session-scoped (cumulative realized loss as a percentage of `initial_cash`); in a backtest there is no real clock, so "daily" spans the whole run. **The starting capital is read from `StrategyInstance::initial_cash`, NOT downcast from `PaperBroker::get_state().initial_cash`** — the old downcast returned 0.0 for any non-Paper `ExecutionTarget` and made `MAX_DAILY_LOSS` a silent no-op in live trading (audit item A1). All callers (`run_backtest_internal`, `PortfolioEngine::new`, `LiveSession::start`) must thread `initial_cash` through; `commands::live.rs` defaults to `DEFAULT_LIVE_INITIAL_CASH = 1_000_000.0` INR and `LiveSession::start` emits a stderr warning if the value is `<= 0.0` so the user notices the cap is inactive. The A1 check is guarded by `risk_max_daily_loss_fires_for_non_paper_broker`; the A2 exit exemption is guarded by `risk_max_orders_does_not_block_stop_loss` / `risk_max_orders_does_not_block_take_profit` / `risk_max_orders_does_not_count_or_block_rule_driven_sell` / `risk_max_orders_exhausted_then_re_armed_after_exit` in `src/strategy/runtime/engine.rs::tests`. (`src/strategy/runtime/engine.rs::check_risk_breach`, `src/strategy/dsl/parser.rs::parse_risk_declaration`.)

**18. Phase 8 — `GatedLiveExecutionApi` is the plugin order gateway.** Live orders can originate from either the strategy engine or a Phase-8 plugin host, and both code paths funnel through `DhanBroker::execute_with_meta` so `MAX_DAILY_LOSS`, market-hours, session pause, the trade-log context, and H3 cancellation cover every real order. `GatedLiveExecutionApi` (`src/plugin/api/execution.rs`) re-runs six gates on every `submit_order` call: (1) a live session is currently active (slot is `Some`), (2) the symbol is in `SymbolMap` and resolves to `Segment::NseEq`, (3) market hours via `is_market_open` (same predicate as `LiveGuard`), (4) `DhanBroker::is_stale()` is `false`, (5) the session's `CancellationToken` is not cancelled, and (6) BUY orders are blocked when the session is paused (SELL orders always pass so plugin-driven exits remain allowed). On every gate pass, the request is converted to a broker `Order`, the `SessionContext` is staged under an RAII guard so the trade-log row attributes to the plugin (`"plugin:<strategy_id>"` / `"<strategy_name> [plugin order]"`), and the call is forwarded to `broker.execute_with_meta(order, "plugin", "")` — the same path the engine uses. `cancel_order` returns a structured error (the broker does not yet expose a cancel endpoint); `positions()` mirrors the read-only path via `block_in_place + Handle::block_on`. The Tauri `HostFactory` closure captures the `live_session` slot, `symbol_map`, `holiday_calendar`, and multi-thread runtime handle so plugin hosts constructed during an active session get `GatedLiveExecutionApi`; hosts constructed when no session is active get `NoopExecutionApi`. `paused_for_entries` on `DhanBroker` is read through the typed `paused_for_entries_snapshot()` getter (L2 hardening); the raw field stays private to plugins. See `plans/live_execution/live_execution_audit.md` Resolution Status.

**18a. C2 — engine splits eval from execution.** Phase 8 added `StrategyEngine::plan_candle(&[Candle]) -> (Vec<LogEntry>, Vec<OrderIntent>)` and `StrategyEngine::execute_intent(intent) -> Vec<LogEntry>` alongside the original `on_candle`. `on_candle` is now a thin wrapper that calls `plan_candle` and discards the intent list — backtests, CLI, and `PortfolioEngine::on_tick` keep their existing call site unchanged. The live tick loop calls `plan_candle` under the engine lock, drops the lock, then executes each intent through a cancellation-aware executor that is being wired in Phase 8 Task #3. `OrderIntent` carries `order`, `rule_id`, `notes` (`"stop_loss"` / `"take_profit"` / empty), and `candle_timestamp`. The intent list is the audit trail: every order the engine planned this candle, in rule order. Backwards compatibility is guarded by `on_candle_preserves_logs_when_run_via_plan_candle` in `src/strategy/runtime/engine.rs::tests`. The full lock-release refactor (release during the await on `execute`) is still Phase 9 multi-session work — `execute_intent` keeps the lock today because extracting `risk_state` and `logger` from `&mut self` is a much larger refactor; H3 cancellation is the practical safety net for now.

**19. Phase 7 Live Trading UI.** The fifth sidebar nav item is `Live`, rendered by `src/screens/Live/LiveScreen.tsx` and built on four sections: status card (with a pulsing green dot when `status === 'Running'` and a stale-loss badge), open positions card (count only until Phase 8 adds `get_live_positions`), controls row (Pause / Resume / Stop — Pause/Resume gated by status), and trade log table. Status is polled by `src/hooks/useLiveStatus.ts` every 5 s; no other component spins up `setInterval` against `getLiveStatus`. Going live requires `LiveConfirmModal` (a three-step pre-flight → ack → confirm modal at `src/components/LiveConfirmModal/`); `requestLiveStart` returns a token and possibly `requiresAck: true`, `acknowledgeLiveTrading` is a pure file write that drops future `requiresAck` flags, `confirmLiveStart` consumes the token with its 90 s TTL. Sticky failure and open-positions notifications flow through `ToastContext` (`src/components/Toast/ToastContext.tsx`) and Tauri event listeners `live_session_failed` / `live_session_stopped_with_positions` registered in `App.tsx`. Browser fallback: every live command throws `"live trading is not available in the browser"` (the wrappers in `src/types/tauri.ts` already do this), the modal swaps Step 1 for a "live trading is only available in the desktop app" notice with only a Cancel button.

## Test Layout

- Per-module unit tests live alongside source as `#[cfg(test)] mod tests` blocks.
- Strategy integration tests live in `src/strategy/tests/` (notably `backtest_integration.rs`).
- A dedicated determinism test guards the same-input-same-output property.
- No frontend test suite is wired up — verify UI changes manually via `npm run tauri dev`.

## Env Requirement

Tauri app requires `DHAN_ACCESS_TOKEN` in `.env` (see `.env.example`); live order placement also requires `DHAN_CLIENT_ID` so Dhan order bodies can include `dhanClientId`. The CLI loads `.env` via `dotenvy::dotenv()`. When the token is missing or Dhan returns no candles, `run_backtest_dsl` falls back to the bundled sample CSV and emits an `eprintln!` warning.
